# Обновление DigitalDoorKey — 13 октября 2026

> Исторический первый этап. Текущее состояние прав доступа и отзыва: [14 октября](aliro-access-policy-2026-10-14.ru.md); [документация и переводы](README.md).

Обновление подготовлено в `codex/ddk-validation-revocation`. Новая прошивка
собирается; проверки NFC, хранения и отзыва проходят на компьютере. Контроллер
выключен, поэтому совместимость новой сборки с настоящим iPhone ещё нужно
подтвердить. Майский рабочий код остаётся в `master`
(`5e68eb66c87e45347455e372264d3e9233f20cd5`).

## Что исправлено

- DigitalDoorKey обновлён до конкретной
  [ревизии 80e4a1e](https://github.com/rednblkx/DigitalDoorKey/tree/80e4a1e14eab3646b62ab3bdad6d2ed01d399375).
  Изменения библиотеки перечислены в [UPSTREAM.md](../aliro-esp32/components/DigitalDoorKey/UPSTREAM.md).
- Неизвестный endpoint больше не становится разрешённым просто потому, что
  подписал запрос собственным ключом. Неверная подпись, повреждённый SELECT и
  неподдерживаемая версия дают отказ без сохранения нового ключа.
- `ClearCredential` удаляет соответствующий endpoint либо издателя со всеми
  его endpoints. Типы evictable/non-evictable учитываются отдельно даже при
  одинаковом номере слота. Отозванный публичный ключ сохраняется в списке
  запрета; снять этот запрет может явное повторное provision через Matter.
- Сохранение после NFC-проверки сравнивает версию данных с актуальной. Старый
  запрос не может вернуть удалённый ключ. Перед фактическим изменением замка
  проверка повторяется на задаче Matter, вместе со статусом пользователя.
- Перезапуск сверяет NFC-записи с сохранёнными слотами Matter. Ошибки записи
  NVS возвращают неуспех; неудачное NFC-сохранение не создаёт разрешённый ключ
  только в оперативной памяти.
- Синхронизация reader identity при загрузке больше не заменяет весь список
  ключей пустым. Существующие iPhone endpoint IDs, FastAuth keys, идентификатор
  считывателя и pairing сохраняются. Формат старых MessagePack-записей читается;
  новые поля добавлены как необязательные.
- Версия выбирается из FCI: при наличии используется Aliro `0x0100`; Apple
  `0x0009` разрешён явно для совместимости. Для v9 сохранены прежние AUTH0/AUTH1
  без Le, CONTROL FLOW и параметры получения криптографических ключей.
- DDK по умолчанию скрывает целиком ключи и бинарные данные в журнале.

## Граница Step-up

Следующий этап реализован отдельно: [перенос валидатора](aliro-porting-2026-10-13.md)
добавляет digest/validity/iteration checks. Ниже сохранено описание первоначального
source snapshot; автоматическое разрешение нового ключа остаётся выключенным.


Проверка подписи документа ещё не является полной проверкой права доступа.
Новая DDK умеет проверять подпись издателя; мы дополнительно связали ключ
документа с подписью устройства в AUTH1. Однако upstream пока не проверяет
весь IssuerSignedItem, сроки, validity iteration и содержимое разрешения.
Требования описаны в §7.4 официальной
[Aliro Specification 1.0](https://csa-iot.org/wp-content/uploads/2026/02/26-42802-001_Aliro_1.0_specification.pdf).

Поэтому прошивка отклоняет неизвестный endpoint даже после криптографически
успешного Step-up. Автоматическое предоставление доступа по документу остаётся
отключённым до реализации полной проверки. Это сохраняет путь для уже
предоставленных Matter-ключей и существующего iPhone-кэша.

Старый кэш сохранён ради совместимости. Обновление не доказывает задним числом,
что каждая запись, добавленная старой логикой, принадлежит владельцу: на стенде
нужно сверить сохранившиеся записи с выданными ключами. Неизвестные новые записи
теперь отклоняются. Это экспериментальная сборка, не сертифицированный выпуск.

## Публикация исходников

Реальные настройки Wi-Fi удалены из исходников Matter controller и перенесены
в локальные параметры сборки. Пустые параметры сохраняют уже настроенную сеть
в NVS. `.env`, локальный CSA PDF и runtime-данные не публикуются.

Старый пароль всё ещё присутствует в приватной истории Git. Существующий
репозиторий нельзя открывать простым изменением visibility. Подготовлен экспорт
в новый снимок без `.git`, старых коммитов, локальных конфигураций, журналов и
root `littlefs.bin`. Последний строится из Svelte-исходников WebUI. Документация
с примерами личных LAN-адресов обезличивается только в экспортируемой копии.

```sh
python3 scripts/export-public-source.py
```

Экспорт содержит manifest с SHA-256 каждого файла. Проверяются точные значения
старых Wi-Fi literals и имеющихся локальных Telegram credentials; дополнительно
дерево проверено Gitleaks 8.30.1. Найдено 47 кандидатов, все относятся к уже
проверенным upstream test fixtures / строкам-маркерам и совпадают с исходными
файлами аудита по содержимому. Новых кандидатов и точных личных секретов нет.
Классификация привязана к хэшам файлов, а не к общему разрешению всех PEM.
Сторонние публичные
тестовые PEM-файлы сохраняются с происхождением, а не маскируются общим ignore.

Область лицензий описана в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md):
проектный Aliro-код имеет существующие commercial source-available условия;
Python PM3, DigitalDoorKey и унаследованные MIT-исходники сохраняют MIT.
Публичность исходников при этих условиях не означает OSI Open Source всего
репозитория. Сайт и GitHub visibility этой работой не менялись.
